## Inventario del esquema

| Retiro | Consumidores que conservan la regla |
| --- | --- |
| Nombres, ISO y códigos de catálogo, extremos de rutas, código de operadora y escalas de ofertas | Validación administrativa, `normalizeCatalogRow`, adaptador OurAirports y resolución de extremos durante la importación. |
| Mes y estado de revisiones ANAC, tipo de movimiento | Validación de período y cobertura mensual, normalización de la fila y transiciones de revisión en `ActividadService`. |
| Evidencia de demora, extremos e identidad de vuelos | `validarOperacion`, preparación de OAG y `VuelosService.importarLote`. |
| Mes, extremos, contadores y demora de las publicaciones OTP | Clave mensual derivada de la fecha operativa y resumen de operaciones finalizadas en el dominio de métricas. |
| Producto, ámbito, granularidad y rango de EUROCONTROL | DTO, lista de productos del worker y lector de planillas. |
| Mes configurado y cobertura BTS | DTO, validación del período y de completitud previa a la promoción. |
| Vista `cantidades_rutas_aeropuerto` | Conteo expresado en TypeScript mediante el ORM tipado, sin SQL manual en el helper. El catálogo, la búsqueda, la proximidad, países y rutas conservan el orden y la paginación en PostgreSQL. El ranking global materializa un conteo por aeropuerto y lo reutiliza para ambos extremos. |

Se conservan PK, FK, unicidad, NOT NULL, índices y el tipo PostGIS `geography(Point,4326)` con índice GiST. Los CHECK restantes protegen la estructura de los registros, la identidad canónica de usuarios y procesos ETL, los valores enumerados, la geometría, las claves de configuración únicas y la coherencia de auditoría. La prueba `reglas-backend.e2e-spec.ts` lista esos CHECK y consulta el catálogo para detectar funciones, triggers, vistas y vistas materializadas propias.

La migración conserva las tablas y columnas de T08. `vuelos` y `historial_vuelos` siguen respaldando la administración y el retiro de filas en OAG/BTS. T10 cambia la persistencia de operaciones a evidencia inmutable por ejecución y T14 retira edición e historial individual. La contracción de sus campos requiere que esos consumidores ya se hayan reemplazado.

## Actualización y recuperación

La base de partida es una instalación verificada con el contrato de T08. Las instalaciones anteriores deben completar las migraciones correspondientes hasta T08 antes de aplicar T09.

1. Detener los escritores, obtener un respaldo completo con `pg_dump -Fc` y verificar que pueda restaurarse en otra instancia con clientes PostgreSQL compatibles. Ensayar el cambio sobre una copia descartable.
2. Desde `backend/`, ejecutar `npx prisma contract emit` y `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f prisma/changes/20261115_esquema_minimo.sql`. La migración es transaccional y elimina objetos conocidos sin cascada.
3. Ejecutar `npx prisma db verify --schema-only --db "$DATABASE_URL"`, `npx prisma db sign --no-advance-ref --db "$DATABASE_URL"` y `npx prisma db verify --db "$DATABASE_URL"` antes de iniciar la versión nueva.
4. Para volver a T08, restaurar el respaldo anterior en una instancia separada y verificarlo con el contrato de T08. Reconciliar cualquier escritura posterior al respaldo antes de volver a conectar el servicio.

La instalación limpia usa `prisma/functions.sql` para habilitar PostGIS, `prisma db init`, `prisma/constraints.sql` y las filas iniciales de `20261115_bloqueos_transaccionales.sql`. El script histórico que instala la vista solo se necesita al reproducir la base T08.

## Evidencia de cierre

Base `56a2697`. Instalación limpia y actualización ensayadas en bases descartables de PostGIS 16, con Redis 7 aislado. Se emitió el contrato anterior, se inicializó la base, se aplicó el recorte T08 y se cargó `test/fixtures/t09-historico.sql`. Tras aplicar `20261115_esquema_minimo.sql`, las filas de las 27 tablas de aplicación permanecieron idénticas. `prisma db verify --schema-only`, firma sin avanzar referencias y verificación completa coincidieron con el contrato de la instalación limpia. No se modificó la base habitual.

- Backend: `npm run build`, `npm run lint` y `npm test -- --runInBand`; 210 pruebas, 39 suites, sin errores de lint.
- Frontend: `npm run build` y `npm test`; 229 pruebas, 38 suites.
- Integración: `npm run test:e2e -- --runInBand`; 63 pruebas, 30 suites, con PostgreSQL/Redis aislados y el catálogo OpenFlights fijado en el README. La nueva prueba de conteos contrasta con el ORM existente y cubre ambos extremos, múltiples ofertas, archivo y aeropuertos sin rutas.
- Revisión independiente: conteos equivalentes y alias correlacionados correctos. Se evitó repetir los conteos por ruta candidata mediante materialización por aeropuerto en el ranking global.
- La eliminación del workflow backend fue confirmada expresamente por el usuario. Los controles anteriores se ejecutaron localmente.
- El desacoplamiento ANAC/EUROCONTROL restante queda explícito en T19; T10 y T14 conservan la contracción pendiente de operaciones e historial.

Medición sintética adicional, con 7.698 aeropuertos y 66.197 ofertas importadas: catálogo de 50 aeropuertos ~152 ms y mapa global de 50 pares ~320 ms. La exploración predeterminada de 100 rutas tarda ~76,4 s; el mismo recorrido con el servicio y la vista de la base `56a2697` tarda ~78,7 s. La lentitud se reproduce en la base anterior; no se presenta como resuelta en T09. Son mediciones locales, sin carga concurrente de usuarios.
