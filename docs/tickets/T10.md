# T10 · Hacer durable el cálculo y la promoción por ingesta

Spec: [SPEC-02](../specs/02-arquitectura-por-contratos.md).
Estado: ready-for-agent, pendiente de dependencias. No implementado por este documento.
Dependencias: [T04](T04.md), [T06](T06.md).
Rama propuesta: `feature/recalculo-durable`.

## Resultado y alcance

Hacer atómica y durable en PostgreSQL la admisión exclusiva de ingestas de operaciones de vuelo. Solicitar cálculo durable por carga validada, recuperar pendientes y promover revisiones completas por población.

Al unificar la admisión, seleccionar el adaptador instalado por capacidad y configuración validada mediante el puerto `AdaptadorOperaciones` de [T05](T05.md).

El refactor de seguimiento comparte un bloqueo transaccional de PostgreSQL entre OAG y BTS y usa las filas pendientes o en ejecución para reservar el cupo después del commit. Un intento BTS que vuelve desde `failed` vuelve a comprobar el cupo antes de leer datos. Completar la recuperación al caer entre commit y encolado. Probar que arrancar otra réplica durante esa ventana preserva la exclusión y medir la espera de escrituras durante el barrido de métricas.

## Aceptación comprobable

- [ ] Operaciones inmutables por ejecución; una carga posterior puede incorporar evidencia rectificada por el proveedor.

- [ ] Caída entre commit y enqueue se recupera
- [ ] Dos solicitudes simultáneas, incluso de proveedores distintos, admiten una sola ingesta. Ante conflicto, la solicitud manual recibe HTTP 409 con ID activo y el cron registra la omisión. Un reinicio recupera o cierra la ejecución antes de admitir otra.
- [ ] Cambiar la fuente publicada requiere autorización explícita capturada para la población. Una ejecución cerrada o sin autorización requerida no puede promoverse.
- [ ] Carga fallida o parcial conserva la publicación vigente. Un reemplazo validado actualiza juntos los conteos y el puntero, incluido un vacío verificado. No elimina las filas anteriores durante la promoción.
- [ ] error solo administrativo.

## Límites y recuperación

Reusar mecanismo durable existente; no agregar outbox duplicado.
Conservar cambios ajenos. Una reversión de código no autoriza pérdida de datos; migraciones requieren procedimiento validado en instancia separada. No push, merge ni acciones destructivas sin autorización explícita.
