# T10 · Hacer durable el cálculo y la promoción por ingesta

Spec: [SPEC-02](../specs/02-arquitectura-por-contratos.md).
Estado: implementado y verificado con datos sintéticos en `feature/integracion-servicios`.
Dependencias: [T04](T04.md), [T06](T06.md).
Rama propuesta: `feature/recalculo-durable`.

## Resultado y alcance

Hacer atómica y durable en PostgreSQL la admisión exclusiva de ingestas de operaciones de vuelo. Solicitar cálculo durable por carga validada, recuperar pendientes y promover revisiones completas por población.

Al unificar la admisión, seleccionar el adaptador instalado por capacidad y configuración validada mediante el puerto `AdaptadorOperaciones` de [T05](T05.md).

El refactor de seguimiento comparte un bloqueo transaccional de PostgreSQL entre OAG y BTS y usa las filas pendientes o en ejecución para reservar el cupo después del commit. Un intento BTS que vuelve desde `failed` vuelve a comprobar el cupo antes de leer datos. Completar la recuperación al caer entre commit y encolado. Probar que arrancar otra réplica durante esa ventana preserva la exclusión y medir la espera de escrituras durante el barrido de métricas.

## Aceptación comprobable

- [x] Operaciones inmutables por ejecución; una carga posterior puede incorporar evidencia rectificada por el proveedor.

- [x] Caída entre commit y enqueue se recupera
- [x] Dos solicitudes simultáneas, incluso de proveedores distintos, admiten una sola ingesta. Ante conflicto, la solicitud manual recibe HTTP 409 con ID activo y el cron registra la omisión. Un reinicio recupera o cierra la ejecución antes de admitir otra.
- [x] Cambiar la fuente publicada requiere autorización explícita capturada para la población. Una ejecución cerrada o sin autorización requerida no puede promoverse.
- [x] Carga fallida o parcial conserva la publicación vigente. Un reemplazo validado actualiza juntos los conteos y el puntero, incluido un vacío verificado. No elimina las filas anteriores durante la promoción.
- [x] Error y estado de actualización solo administrativos.

## Evidencia de la rama

Base `1ef22dc`. Los E2E de OAG y BTS usan respuestas HTTP y ZIP mensuales sintéticos. Cubren reintentos, pérdida de encolado, publicación anterior ante fallos, revisión de operaciones y métricas, autorización por población y el retiro verificado de una población en un mes completo de BTS. Dos instancias con conexiones independientes a PostgreSQL y Redis reproducen el arranque de una réplica con la admisión BTS confirmada y el encolado original interrumpido. La segunda recupera el mismo ID y OAG recibe 409 con ese ID. El E2E de métricas comprueba la inmutabilidad de la evidencia y el acceso administrativo al estado de actualización.

La revisión independiente detectó una carrera entre el barrido de recuperación y el commit de la carga validada. El cierre de error exige el mismo intento y que todavía no esté lista para publicar. El E2E también detectó que la consulta de poblaciones ausentes usaba campos ajenos a la clave del tramo de OAG. Ahora filtra con los dos IDs de aeropuerto.

En PostgreSQL local, con dos conexiones y 100 aerolíneas sintéticas, tres escrituras administrativas durante un barrido tardaron 403, 316 y 286 ms. Las escrituras de control tardaron 89, 17 y 16 ms. El barrido completo tardó entre 304 y 511 ms. La medición es exploratoria e incluye conexión de aplicación, consultas y commit.

Pasaron `npm run build` en ambos proyectos, `npm run lint` en backend y las pruebas unitarias de ambos proyectos (210 backend y 229 frontend). Pasaron también los E2E de OAG, BTS, operaciones y métricas, mapa, servicios, pipelines y encolado real. Prisma emitió avisos preexistentes de validación de nombres SQL. El piloto de OAG sigue en T12. Una respuesta vacía o con identidades faltantes de OAG conserva la publicación vigente porque el contrato disponible no certifica su cobertura.

## Actualización y recuperación

Ensayar sobre una copia, detener los escritores y emitir el contrato con `npx prisma contract emit` desde `backend/`. En bases existentes con el esquema de la rama base, aplicar `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f prisma/changes/20261120_operaciones_por_ejecucion.sql`, verificar con `npx prisma db verify --schema-only --db "$DATABASE_URL"`, firmar con `npx prisma db sign --no-advance-ref --db "$DATABASE_URL"` y repetir la verificación completa. La instalación limpia ya usa el contrato nuevo.

La copia de actualización conservó el ID de vuelo, la observación histórica, la entrada de auditoría y su relación con la ejecución y métrica publicada. El historial previo y las columnas de edición quedan disponibles para T14. Una versión anterior del código necesita el índice único global. Después de aceptar revisiones con la misma identidad en ejecuciones distintas, cualquier vuelta a esa versión requiere conciliar esos registros en una copia y validar el esquema anterior antes de reemplazar la instancia.
